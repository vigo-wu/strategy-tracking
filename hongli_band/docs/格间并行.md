# 格间并行（local_bt 网格）

> 调度已改为 **扁平全局 walk 池**（探针后把各格 walk 铺平进同一层 ProcessPool，格间与格内共用额度）。不要按下面旧表实现「一格一个 worker、格内钉死 1」。Queue 只能 initializer 继承、失败分流、Windows spawn 下 `app.py` 跳过 `st.*`，这几条仍有效。现行契约见 `.cursor/skills/qmt-local-bt-grid`。

16 格、每格 2 段 walk（调参篮 + 盲测篮）时，格内进程池可以把两段 walk 一起跑：init 探针只校验指纹、不回放 K 线。真正的大头加速仍是 **格子之间** 并行。每格写独立目录 `report/grid/<sweep>/<cell>/`，格子之间无共享钱包，可以并行。

只开 **一层池（格间）**。格间并行时格内 walk 强制串行，避免进程数 × 格数爆炸。

实现入口：`hongli_band/scripts/local_bt/grid_run.py`。契约见 `.cursor/skills/qmt-local-bt-grid`。

## 旋钮语义

不新增第二套 UI。`grid_workers` / CLI `--workers` = **格间进程数**：

| 取值 | 格间 | 格内 walk |
| :--- | :--- | :--- |
| `<=0` | 自动 `min(n_cells, cpu, 8)` | 钉死 1 |
| `1` | 串行 | 仅 `jobs/cell>2`（开 SMA/EMA）时 `resolve_workers(0, n_jobs)` |
| `>=2` | ProcessPool，上限 8 | 钉死 1 |
| `--cell` | 强制 1，不开池 | 同上 |

`0=自动` 会让侧栏缓存的旧 `grid_workers=0` 从串行变成最多 8 路，内存/磁盘会上去。侧栏文案写清「格间进程数（0=自动，上限 8）」。

inner 必须单独算，不能把同一个数字既当格间又当格内：否则 `workers=1` 时格内也被钉死，SMA/EMA 加速丢失。

## 进程模型

```
run_sweep 写完 spec.json / freeze.json、prune 之后
  cw<=1 → for cell in cells: run_cell(...)
  cw>1  → spawn ProcessPool，一格一个 run_cell_job
           主进程短 timeout wait(future) + drain Queue
           全部成功再 summarize；失败先 raise，不汇总
```

- 入口必须是 **模块级** `run_cell_job(payload) -> dict`（Windows spawn 才能 pickle）。payload 含 `cell / jobs / cell_dir / defaults / inner_workers`；路径用 `str`。
- `initializer` 补 `local_bt` / `scripts` 到 `sys.path`（同 `batch_job.init_worker`）。
- worker 禁止调用 `st.*`，禁止闭包捕获 Streamlit。
- 不必改 `book_backtest`。格子目录已隔离。

## 进度 Queue：只能继承，不能 submit

计划里「Queue 放进 `submit` 的 payload」在 Windows spawn 上会立刻失败：

```
RuntimeError: Queue objects should only be shared between processes through inheritance
```

现象：确认开跑后目录里只有 `spec.json` / `freeze.json`，没有 `cell_meta.json`。

正确做法：Queue 走 **initializer 的 initargs**（inheritance），不要放进 pickled payload。

```python
ctx = get_context("spawn")
q = ctx.Queue()
with ProcessPoolExecutor(
    max_workers=cw,
    mp_context=ctx,
    initializer=init_cell_pool,       # 调 init_worker，再把 q 挂到模块全局
    initargs=(str(HERE), q),
) as ex:
    ex.submit(run_cell_job, payload)  # payload 禁止带 progress_queue
```

子进程用模块全局取队列，只 `put((cid, done, tot, label))`。主进程轮询 future 时 **随时 drain**，不要等整格 `as_completed` 才刷新。

进度：`frac = sum(各格已完成 walk) / (n_cells * n_jobs)`。stdout 交错时带 `[cell_id]` 前缀。init 探针写 `probe_init.txt`，进度标「探针 init」，不要把第一段 walk 再标成探针。

## 失败与回退

两种失败不要混：

| 来源 | 处理 |
| :--- | :--- |
| `run_cell_job` 返回 `{ok: False}`（探针指纹 / walk 失败） | 升成 `GridError`，cancel **尚未开始** 的 future，不 summarize、不回退串行 |
| `fut.result()` 抛出（pickle / BrokenProcessPool / Queue 传参错误） | **原样再抛**，`run_cells` 打 WARN 后回退格间串行 |

`cancel_futures` 停不了已经在跑的格；失败后仍可能有多格写完盘。不要宣称「立即中止所有格」。

从 UI 后台线程起 spawn 池可以工作（线程 `daemon=False` 即可）。基础设施失败才回退串行，不要因为「在线程里」就默认不用池。

## Windows spawn 会再 import Streamlit 入口

`streamlit run .../app.py` 时 `__main__` 就是 `app.py`。格间池的子进程会再 import 这份文件，没有 `ScriptRunContext`，一碰 `st.set_page_config` / `@st.dialog` 就刷：

```
missing ScriptRunContext! This warning can be ignored when running in bare mode.
```

`app.py` 在 import Streamlit / `grid_ui` **之前** 判断 `multiprocessing.current_process().name != "MainProcess"`：子进程只完成 import，跳过全部 `st.*` 和页面渲染。真正干活的仍是 `grid_run.run_cell_job`。

探测上下文时用 `get_script_run_ctx(suppress_warning=True)`。直接调 `get_script_run_ctx()` 会自己打出上面那条警告。

改完必须重启 Streamlit。

## 测试

mock 调度即可，不要真开 4 进程测「走池还是走串行」：

- `workers=1`：串行 for，调用次数 = 格数
- `workers=4`、4 格：`inner_workers=1`，dispatch 走池
- 某格 `{ok: False}`：未开始的 future 被 cancel；不调用 summarize
- `workers=0`、9 格：auto ≤ 8
- 池抛 `RuntimeError`：回退串行；池抛 `GridError`：不回退
- submit 的 payload **没有** `progress_queue`

只 mock 测不出 Queue 继承问题。必须另有一条 **后台线程 + spawn 池 + initializer 传 Queue** 的实测：空 jobs 应返回「无 job」，而不是 `Queue objects should only be shared…`。`import app`（模块名 `app`）不等于子进程把 `app.py` 当 `__main__`。

## 不要做

- 格间 + 格内两层池
- 把 `Queue` 放进 `submit` 参数 / payload
- 把 `fut.result()` 的基础设施异常包成 `GridError`（回退会被挡住）
- worker 里调用 Streamlit
- 把 16 格自动裁到 8；这轮不做 CSV / bundle 缓存
