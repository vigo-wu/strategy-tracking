# 网格并行经验（local_bt）

hongli_band 网格从「格间 ProcessPool」改到 **一层全局 walk 池**，再补上全局进度条。本文记踩坑与现行口径，不替代 `.cursor/skills/qmt-local-bt-grid` 契约。

实现：`hongli_band/scripts/local_bt/grid_run.py`、`grid_ui.py`、`app.py`。单测：`test_grid_run.py`。

## 现行模型（先看这张）

```
run_sweep 写 spec / freeze、prune
  探针：主进程按格串行（dummy init，不回放 K 线）
  cw<=1 → 串行 run_cell（格内也钉死 1）
  cw>=2 → 把各格 walk 铺平，同一层 spawn ProcessPool
           入口 run_walk_job（模块级，可 pickle）
           主进程：drain Queue → wait(future, 0.2s) → 每轮最多刷一次 UI
           全部成功再 summarize
```

| 旋钮 | 含义 |
| :--- | :--- |
| `workers<=0` | `min(总 walk 数, CPU)`，**无硬编码 8** |
| `workers==1` | 全串行 |
| `workers>=2` | 池大小，只夹 walk 数 |
| CLI `--workers` | **不夹 16** |
| 侧栏 `grid_workers` | `max_value=16`（UI 保护，不是硬件常数） |

总 walk 数 = `n_cells × n_jobs`。每格最多 6 段：调参篮 / 盲测篮 ×（可选）SMA / EMA。`--cell` 只过滤格子，该格多段 walk 仍可进池。

格子目录 `report/grid/<sweep>/<cell>/` 互不共享钱包，**可以**并行。加速来自同时跑多段 walk，不是「一格一个进程再在格内开第二层池」。

## 1. 不要嵌套两层 ProcessPool

最初方案：格间一层池（一格一个 `run_cell_job`），格内 walk 钉死 1，避免 `进程数 × 格数` 爆炸。上限 8 写进了表，其实抄的是 `run.py` `resolve_workers` 的历史封顶，**不是这台机器的物理核数**。

后来要格间+格内同时开。Windows spawn 上 **禁止** 池里再开池：子进程再 `ProcessPoolExecutor` 会再 import、再抢核，内存和句柄一起爆。正确做法是铺平：

- 探针留在父进程（指纹失败应整 sweep 停，不必占 worker）
- 通过后把 `(cell, sample, basket)` 打成 walk payload
- **一层**池跑 `run_walk_job`

`run_cell(..., workers>1)` 的格内池只留给「有人直接调 `run_cell`」。`run_cells` 走池时传给 `run_cell` 的 workers 恒为 1（回退串行同此）。

## 2. workers 数字不要复用两套语义

同一个整数不能既当格间路数又当格内路数。否则 `workers=1`（用户要串行网格）会把格内 SMA/EMA 也钉死。扁平池之后这个问题消失：只有一个全局额度。

侧栏文案写「将开 N 路（X 格 × Y walk）」，用 `resolve_pool_workers` 预览，避免 `0=自动` 时用户以为还是串行。

本机经验（24 物理核 / 32 逻辑处理器 / 32GB RAM）：

- 侧栏默认 `0` 会开到最多 **32 路**（逻辑核）
- 先用 **16** 比较稳；要对齐物理核用 CLI `--workers 24`
- walk 是拼接脚本 + 日线 CSV，内存随路数涨，不要按「核数=可开路数」一次拉满

## 3. Windows spawn：Queue 只能继承

计划里「把 Queue 放进 `submit` 的 payload」会立刻失败：

```
RuntimeError: Queue objects should only be shared between processes through inheritance
```

现象：点了开跑，目录里只有 `spec.json` / `freeze.json`，没有 `cell_meta.json`（worker 根本没起来，或主进程在 pickle 阶段就炸）。

正确做法：

```python
ctx = get_context("spawn")
q = ctx.Queue()
with ProcessPoolExecutor(
    max_workers=cw,
    mp_context=ctx,
    initializer=init_walk_pool,   # batch_job.init_worker + 挂模块全局 _WALK_PROGRESS_Q
    initargs=(str(HERE), q),
) as ex:
    ex.submit(run_walk_job, payload)  # payload 禁止 progress_queue
```

Worker 从模块全局 `_WALK_PROGRESS_Q` 取队列。入口必须是 **模块级函数**（闭包 / `st.*` / 绑了 Queue 的对象都 pickle 不了）。

从 Streamlit 后台线程起 spawn 池可以工作，线程 `daemon=False`。不要因为「在线程里」就默认不用池。

## 4. spawn 会再 import `app.py`

`streamlit run .../app.py` 时 `__main__` 就是 `app.py`。子进程会再执行这份文件，没有 `ScriptRunContext`，一碰 `st.set_page_config` / `@st.dialog` 就刷：

```
missing ScriptRunContext! This warning can be ignored when running in bare mode.
```

`app.py` 在 import Streamlit / `grid_ui` **之前**判断 `current_process().name != "MainProcess"`：worker 只做 import，跳过全部 `st.*` 和页面。干活的是 `grid_run.run_walk_job`。

探测上下文必须 `get_script_run_ctx(suppress_warning=True)`。直接 `get_script_run_ctx()` 会自己打出上面那条警告。

改完必须 **重启 Streamlit**。`import app`（模块名 `app`）不等于子进程把 `app.py` 当 `__main__`，单测 mock 不到这条。

## 5. 进度：全局 walk，不要「当前格 + 最后一次 inner」

池开 16 路时，旧 UI 用 `sum(各格已完成 walk) + 最后一次 inner/total`：

- 条子长时间不动（inner 被下一格的 0 冲掉，或根本收不到 bar）
- status 在格子间乱跳
- worker **看不见兄弟 walk**，上报「本格完成了几段」是错的

现行口径：

\[
frac = \min\left(1,\ \frac{completed + \sum_j done_j/total_j}{n_{cells}\times n_{jobs}}\right)
\]

- `completed`：主进程按 **future 完成数**（全局 walk，不是按格覆盖）
- `inflight[job_key]`：该段 `walk_done/walk_total`；开工无 total 时记 0
- `job_key`：`cell_id|sample|basket`
- **先 `pop(job_key)` 再 `completed += 1`**，否则最后一根 bar=1.0 会双计
- 失败 future 同样 `pop`（`drop`，不增加 completed）；已 pop 的迟到 `bar` 忽略
- Queue 只发 `start` / `bar`，不发 `done`（完成以 future 为准）
- worker 只报 **自己这一段** 的 bar；节流仍用 `book_backtest.should_emit_walk_progress`（约 40 步/段 + 换年），**不要改** `book_backtest`
- 主进程每轮 **先 drain 完 Queue 再 wait**；drain 只更新 `WalkProgress`，**每轮最多回调 UI 一次**（16 路 × 40 次 bar 不能每条都 `st.progress`）
- 探针：`phase="probe"`，`probe_done/probe_total`，status 写 `探针 k/n_cells`，**不占** walk 分母（条子停在 0）。漏掉 `phase` 时 `_run_now` 会把 `tot=n_jobs` 当成全局分母
- 串行（`cw<=1`）在 `run_cells` 外包一层回调，**不改** `run_cell` 签名；单测仍直接测 per-cell
- UI 文案：`8.3/32 walk · 16 路`；stdout：`[job_key] 8.3/32 walk · N 路`，不要再打 per-cell `done/n_jobs`
- 残留：探针阶段条子停在 0；status 只显示当前这条 label，不列全部在跑 walk

## 6. 失败不要混成一种

| 来源 | 处理 |
| :--- | :--- |
| walk 返回 `{ok: False}`（探针指纹 / 回放失败） | 升 `GridError`，cancel 尚未开始的 future，**不** summarize、**不**回退串行 |
| `fut.result()` 抛出（pickle / BrokenProcessPool / Queue 传参） | **原样再抛**，`run_cells` 打 WARN 后回退串行 |

不要把基础设施异常包成 `GridError`，否则回退被挡住。`cancel` 停不了已经在跑的 walk；失败后仍可能有多段写完盘。不要宣称「立即中止」。

回退时跳过已全部 walk 成功的格子。`succeeded` 必须在循环里 **原地 add**，不要等函数返回再赋值——赋值前异常会丢掉「哪些格已经跑完」。

## 7. 测试：mock 调度 + 一条真 spawn

mock 即可覆盖调度，不要真开 4 进程测「走池还是走串行」：

- `workers=1`：串行 `run_cell`，次数 = 格数，不开池
- `workers=4`、4 格 × 2 walk：提交 8 个 `run_walk_job`，payload 无 `progress_queue`
- `{ok: False}`：未开始的 future 被 cancel；不调用 summarize
- `workers=0`：`min(n_walks, cpu)`，可以大于 8（例如 cpu=32、walk=9 → 9）
- CLI `--workers 24` 不被夹成 16
- 池抛 `RuntimeError`：回退串行，跳过已成功格；池抛 `GridError`：不回退
- `WalkProgress`：3 完成 + 两段 inflight 各 0.5、分母 8 → frac=0.5；先 pop 再 +1 不会双计；迟到 bar 忽略
- 直接调 `run_cell` 的 bar 标签用例仍过（不走串行包装）

Queue 继承 mock 测不出。必须另有一条 **后台线程 + spawn 池 + initializer 传 Queue**：空 payload 应返回「无 job」，而不是 `Queue objects should only be shared…`。

## 不要做

- 格间池再套格内 ProcessPool
- 把 `Queue` 放进 `submit` 参数 / payload
- worker 上报「本格完成了几段 walk」
- 进度用 `sum(cell_done) + 最后一次 inner`，或每个 bar 都 `st.progress`
- 把 `fut.result()` 的基础设施异常包成 `GridError`
- worker 里调用 Streamlit
- 把自动路数封顶成 8（那是别的函数的历史常数）
- 为扫参改主题 `config.py` / 手改 QMT 终端 GBK
- 改 `book_backtest` 来接进度（节流已经够用）
